# Подпись Android-клиента

## Эталонный отпечаток

Каждая релизная сборка должна давать ровно этот отпечаток:

```
SHA-256  c9:21:a6:79:45:92:05:f7:e4:d6:48:15:ce:c5:ca:b1:b7:44:4a:41:79:4c:fd:95:18:ba:84:9b:f4:b6:6a:66
владелец CN=Method Team, OU=Method Team, O=Method Team Ltd.,
         L=Saint-Petersburg, ST=Saint-Petersburg, C=RU
ключ     RSA 4096
```

Отпечаток — не секрет: он есть в каждом опубликованном APK и служит ровно
для того, чтобы отличить настоящую сборку от чужой. Секрет — пароль и сам
файл ключа.

## Как сверить

```sh
apksigner verify --print-certs -v dist/Method-android-<версия>.apk
```

Не совпало — сборка подписана ДРУГИМ ключом. Публиковать её нельзя: Android
опознаёт обновление по подписи, и такая сборка не встанет поверх выпущенной,
а потребует удалить клиент вместе со всеми настройками.

## Где ключ

`~/.method-keys/method-release.jks`, права 600, каталог 700. В репозитории
его нет и быть не должно — `.gitignore` закрывает `*.keystore`, `*.jks`,
`*.p12`.

Пароль знает только владелец. Скрипты его не принимают, не хранят и не
печатают: пароль в аргументах виден в списке процессов, в переменных
окружения — наследуется дочерними процессами и попадает в дампы.

## Что произойдёт, если ключ потерять

Ничего исправить будет нельзя. Обновления для уже установленных копий выпустить
не выйдет: сборка с другим ключом для системы — другое приложение. Людям
придётся удалить клиент и потерять подписки, сценарии и правила по
приложениям.

Поэтому: пароль в менеджере паролей, копия файла — на отдельном носителе,
не на том же диске.

## Сборка

```sh
# отладка — одноразовый ключ, генерируется на месте
./build-apk.sh

# релиз — спросит пароль у терминала
METHOD_VERSION_CODE=<N> METHOD_VERSION_NAME=<x.y.z> METHOD_RELEASE=1 ./build-apk.sh
```

`versionCode` обязан расти: Android откажется ставить сборку с номером
меньше или равным установленному.
