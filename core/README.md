# Core — оркестратор маршрутов

Ядро, которое решает, **каким маршрутом** идти трафику, и граница C, через
которую это решение забирает клиент на Swift.

| Каталог | Что это |
|---------|---------|
| `method-core/` | ядро: модель (ось, маршрут, полоса), оценка качества, гистерезис, прогон на записанном логе |
| `method-core-ffi/` | граница C: дескрипторы, плоские структуры, коды возврата, ловля паник |
| `include/method_core.h` | заголовок — единственное полное описание интерфейса и правила владения памятью |
| `swift/` | обёртка Swift поверх границы и исполняемый сценарий поверх неё |
| `Scripts/build-macos.sh` | сборка статики для приложения macOS |
| `build/` | результат сборки (в git не попадает) |

Ядро отвечает на один вопрос: **какой маршрут в какую полосу поставить прямо
сейчас и почему**. Не подключает, не измеряет, не рисует.

---

## Зачем вообще граница

Логика выбора маршрута — самая коварная часть клиента. Она ошибается не
падением, а тихо: переключается на маршрут, который через двадцать секунд
умрёт; дребезжит между двумя одинаково плохими; держится за мёртвый, потому что
одна проба случайно прошла. Такие ошибки видно только на длинных
последовательностях событий, и в живом клиенте они не воспроизводятся: чтобы
повторить, нужна та же сеть в ту же минуту.

Отсюда всё остальное. Ядро вынесено в отдельный крейт **без доступа к сети и к
часам**: время и результаты проб подаются снаружи, решение — чистая функция
входа. Тогда набор измерений можно записать в файл и прогнать через движок
целиком (`method-core/src/replay.rs`) — без туннеля, без нод, без интернета — и
проверить не «не упало ли», а **сколько раз переключились и в какой момент**.
Гистерезис иначе настраивается вслепую.

Граница C — цена этого решения: Swift не умеет звать Rust напрямую, между ними
обязан лежать интерфейс на C. Всё, что через него проходит, описано в
[`include/method_core.h`](include/method_core.h) — заголовок написан руками и
объясняет каждое правило на месте.

## Почему в том же процессе и статикой

**Тот же процесс.** Ядро само по себе не может ничего: не открывает сокетов, не
поднимает туннель, не имеет прав. Выносить его в отдельный процесс значило бы
завести IPC, супервизор и ещё один способ сломаться («процесс решений умер»)
ради компонента, который физически ничего не делает. Права root нужны не ему, а
sing-box — тот и живёт в LaunchDaemon (см. корневой `CLAUDE.md`, §3).

Риск, ради которого обычно и городят отдельный процесс — падение из-за ошибки в
чужом коде, — закрыт на самой границе: паника не пересекает её, а превращает
движок в отравленный (`MC_POISONED`). Приложение остаётся живым и знает, что
случилось.

**Статикой.** Динамическая библиотека внутри бандла — это своя подпись, своя
запись в `Frameworks/` и свой путь загрузки через `@rpath`: три способа сломать
сборку там, где статика не ломается никак. Важнее второе: `.dylib` можно
подменить на устаревшую версию, и приложение запустится, а расхождение вылезет
уже в работе. Статика проверяется **на компоновке**: не совпали символы —
сборка упала, и никуда не поехала.

Отсюда же правило: пересобрал Rust — пересобери приложение. Xcode сам про
изменившийся `.a` не узнает.

## Почему ядро не знает про sing-box

В ядре нет ни строчки про sing-box: ни имён outbound'ов, ни JSON конфигурации,
ни Clash API. Оно выдаёт `SELECT{полоса, маршрут}`, а превращает это в конфиг
уже клиент (на macOS — `SingBoxConfigBuilder`). Причин три, и все практические.

1. **Проверяемость.** Знай ядро про sing-box — прогон на записанном логе
   потребовал бы sing-box. Проверять пришлось бы связку, а не логику выбора.
2. **Ядро переживёт движок туннеля.** Слой туннеля уже запланировано менять:
   когда появится платный аккаунт Apple, LaunchDaemon уступит место
   NetworkExtension. Логика выбора маршрута при этом не меняется вообще — если
   она не знает, чем туннель поднимается, менять в ней нечего.
3. **Клиентов больше одного.** macOS, Windows и Android живут на разных
   движках и разных языках, а решают одну задачу. Общим может быть ядро —
   но ровно до тех пор, пока в нём нет ничего про конкретный движок.

По той же причине ядро не читает часы: `Instant` — миллисекунды **монотонных**
часов, которые подаёт вызывающий. Стенные часы прыгают при синхронизации и
после сна, а прыжок назад превратил бы остывание после переключения в вечный
запрет.

## Сборка

```sh
cd Core
sh Scripts/build-macos.sh
```

Скрипт собирает release-статику, кладёт её и заголовок в `build/`, печатает
архитектуры, число экспортированных символов и **точные строки для настроек
Xcode**. Проект macOS собирается XcodeGen — эти строки идут в `project.yml`.

Если цель `x86_64-apple-darwin` установлена, скрипт собирает и её и склеивает
универсальную библиотеку через `lipo`. Если нет — собирает только arm64 и
предупреждает: на Intel-маках такое приложение не запустится (Rosetta переводит
x86_64 в arm64, а не наоборот), и у цели должно стоять `ARCHS = arm64`. Сам
скрипт ничего не устанавливает.

## Проверка

```sh
cargo test -q                                   # 78 тестов: 68 ядра + 10 границы
sh method-core-ffi/tests/run_abi.sh --release   # сквозной сценарий настоящим компилятором C
MC_LEAKS=1 sh method-core-ffi/tests/run_abi.sh  # то же под leaks(1)
```

`cargo test` проверяет только то, что Rust согласен сам с собой. Заголовок при
этом может врать, поэтому `run_abi.sh` компилирует программу на C **из
настоящего заголовка** и линкует её с настоящей статикой.

## Размер

Архив весит около 20 МБ и пугает зря: девять из них — стандартная библиотека
Rust с отладочной информацией, и до приложения она не доезжает. Компоновщик
берёт только затронутое, поэтому реальный вклад — **около 800 КБ** даже если
принудительно втянуть все 33 экспортируемые функции. Скрипт сборки меряет это
число каждый раз (собирает пустую программу с `-u` на каждый символ и вычитает
пустую же без библиотеки), чтобы оценка не превращалась в предание.

Условие — включённое отсечение мёртвого кода (`DEAD_CODE_STRIPPING = YES`, в
Release у Xcode стоит по умолчанию). Без него вклад 2,0 МБ вместо 818 КБ, то
есть в два с половиной раза больше.

Уменьшать дальше нечего, и это замерено, а не предположено:

| Что пробовали | Архив | Вклад в бинарь |
|---------------|-------|----------------|
| как собрано сейчас (`opt-level = 3`, `lto = true`) | 20,3 МБ | 818 КБ |
| `opt-level = "s"` | 21,7 МБ | 996 КБ |
| `opt-level = "z"` | 21,3 МБ | 1048 КБ |
| `strip -S` по готовому архиву | 14,4 МБ | 785 КБ |

Оптимизация по размеру делает **хуже по обоим числам**: и архив толще, и в
приложение приезжает больше. `strip -S` ужимает архив ощутимо, но в приложении
экономит 33 КБ, а выбрасывает всю отладочную информацию, какая там есть, —
принадлежит она стандартной библиотеке, и по ней читаются её кадры в стеке
пойманной паники. Тридцать три килобайта того не стоят, и скрипт архив не
трогает.

Отдельно стоит знать: **у наших собственных кадров номеров строк нет и сейчас** —
в release-профиле отладочная информация не создаётся вовсе. Если однажды понадобится
читать стек паники по именам файлов, это `debug = 1` в `[profile.release]`, и
цена вопроса — размер архива, а не приложения.
